## 3. R2 · 审核链改造

### 3.1 目标链路

```
advanced 投稿 ─┬→ 邀请他的 admin 审
               └→ 超管审（兜底）
admin 投稿 ──────→ 超管审（唯一）
超管 ────────────→ 不能投稿（D35）
评论 ────────────→ 按同样的归属规则审（评论 RPC 已在用 can_review_owner）
```

### 3.2 三处改动

| # | 改动 | 细节 |
|---|---|---|
| 1 | `force_record_review()` | 去掉 `has_any_role(['admin'])` 分支，**所有非超管角色一律 `pending`** 并清空 `reviewed_*`。历史已 `visible` 的数据不回溯 |
| 2 | `can_review_owner()` 删掉自审旁路 | 第一条 `p_owner = auth.uid() → true` 删除。保留：超管 → 任意 owner；admin → 自己邀请的 |
| 3 | `can_review_owner()` 超管改全量 | 超管分支从「`invited_by is null`」改为 `true`（D33，修订 D28） |

### 3.3 代价（必须知道）

- **超管成为 admin 投稿的唯一审核人**：admin 的 `invited_by` 是 null，其他 admin 审不到，只能超管。
- **admin 每次编辑自己的记录都会重新进待审**：因为触发器对 update 也生效。这是"内容要审"的必然结果，换来的是不能靠编辑绕过审核。
- 历史数据不动：已经 `visible` 的 admin 内容继续可见，不回滚。

### 3.4 超时升级（替代"每条都通知超管"）

- 待审超过 **12 小时**未处理 → 给超管发一条 `notifications(kind='review_escalated')`
- **不用 cron**：超管打开审核弹窗时客户端调 `escalate_stale_pending()`，函数内部做两件事：
  1. 找出 `review_status='pending'` 且 `updated_at < now() - interval '12 hours'` 的记录
  2. 对每一条，**查重**（同 `target_id` + `kind='review_escalated'` 且 24h 内已有则跳过），再插入通知
- 幂等、零额外组件（符合 D12：不引入 Edge Function）
- 通知文案：「有 N 条待审已超过 12 小时未处理」，点开进审核弹窗

### 3.5 「最近处理」列表（满足"超管代审要有标记"）

- 新增 `list_recent_reviews(p_limit)`：最近 N 条已审记录（`reviewed_at` 倒序），带 `reviewer_nickname` / `reviewer_role`
- 前端放在审核弹窗底部：每条显示「由 超管 xxx 代审 · 时间」
- **不做**"往待审列表里插一条已处理的" —— 已审的本来就不该在待审里

## 4. R1 · 已驳回记录处置

### 4.1 队列与权限

- 条件：`state = 1 and review_status = 'rejected' and hidden_reason is null`
- 范围：`can_review_owner(owner_id)` —— admin 看自己邀请的，**超管看全量**（D33 之后成立）
- 入口：**审核弹窗第三栏「已驳回」**（不放通知页，理由见 D34）

### 4.2 两个动作

| 动作 | 谁能做 | 行为 |
|---|---|---|
| **再次提醒** | admin / 超管 | `remind_rejected(p_type, p_id)` → 给作者插 `kind='record_reminder'` 通知。**同一条记录 24h 内只发一次**（查 `notifications` 最近一条判断），防刷屏 |
| **物理删除** | **仅超管** | 扩展现有 `purge_record`：允许来源 `state=0`（回收站）**或** `state=1 and review_status='rejected'`。删除前先插 `kind='record_deleted'` 通知（target 置空）+ 写 `admin_actions` 审计；删完 bump 版本、返回孤儿图路径 |

> 管理员**没有**物理删除权限（用户明确要求：所有物理删除只有超管）。

### 4.3 通知类型扩展

`notifications.kind` 增加：`record_reminder`、`record_deleted`、`review_escalated`。
`record_deleted` 的 `target_type/target_id` **置空**（记录马上就没了，点开详情会 404）；客户端点击这类通知不跳转。

### 4.4 72 小时强调

- 前端用 `reviewed_at` 算天数：`> 72h` 时卡片边框换成 `--warning`，并显示「已驳回 N 天」
- 不改数据结构，纯展示

## 5. R3 · 超管权限边界

### 5.1 两类写权限（必须分开，别一刀切）

| 类型 | 谁有 | 判定 |
|---|---|---|
| **内容写**：新增 / 编辑 / 评论 / 图片上传 | advanced、admin | `can_write_records()` + Storage 策略 |
| **管理写**：审核、停用/恢复账号、改角色、回收站、文案、孤儿图 | admin、**superadmin** | 各自 RPC 内的 `is_superadmin()` / `can_review_owner()` |

> 所以"收回超管内容写权限"**不影响**回收站、审核、文案管理 —— 它们本来就不依赖 `can_write_records()`。

### 5.2 三处改动

1. **`auth.canWrite`**（`stores/auth.ts:53`）去掉 `superadmin` → 前端不再显示新增/编辑/上传入口
2. **`create_comment`** 加 `if is_superadmin() then raise 'FORBIDDEN'`；`CommentSection` 对超管隐藏输入框并显示「超级管理员不参与评论」
3. 后端 `can_write_records()` **保持不变**（本来就不含超管），只是前端对齐

### 5.3 副作用

超管代审时想留说明，只能写进 `review_note`（驳回原因），评论渠道关闭。

## 9. 风险与回滚

| 风险 | 等级 | 缓解 |
|---|---|---|
| 超管成为唯一审核人，人不在线就积压 | 中 | T8.5 超时升级通知；审核队列本来就能批量处理 |
| admin 编辑自己的记录反复进待审 | 中 | 这是"内容要审"的必然代价；如需放宽，改成"仅内容变化才重审"（需 diff，暂不做） |
| 去掉自审影响其他流程 | 低 | `can_review_owner` 还用于可见范围判断，删除自审分支后要跑一遍：作者看自己内容走的是 `owner_id = auth.uid()` 的 RLS，不依赖这个函数 |
| 通知类型扩展遗漏 | 低 | 三处（建表约束、`notification_counts`、`list_notifications` 的 scope 映射）一起改 |
| 物理删除不可逆 | 高 | 仅超管 + 二次确认 + `admin_actions` 整行快照 |

**回滚**：代码 `git revert`；数据库反向 migration 恢复三个函数（策略/约束用 `create or replace` 覆盖即可）。已删除的记录和图片不可恢复 —— 这是 R1 唯一的不可逆点。
