## 1. 表结构

### 1.1 用户资料

```sql
create table profiles (
  id          uuid primary key references auth.users(id) on delete cascade,
  nickname    text not null,
  avatar      text,                    -- 内置头像 key：avatar-boy / avatar-girl（null = 按性别回落）
  gender      text not null default 'male' check (gender in ('male','female')),  -- 019
  role        text not null default 'viewer' check (role in ('viewer','advanced','admin','superadmin')),
  created_at  timestamptz not null default now(),
  constraint profiles_nickname_check check (char_length(btrim(nickname)) between 1 and 24)
);

-- 注册后自动建档（019 起同时写入性别）
create or replace function handle_new_user() returns trigger
language plpgsql security definer set search_path = public as $$
declare
  meta_nickname text;
  meta_gender   text;
begin
  meta_nickname := nullif(btrim(coalesce(new.raw_user_meta_data->>'nickname', '')), '');
  meta_gender   := new.raw_user_meta_data->>'gender';

  insert into profiles (id, nickname, gender)
  values (
    new.id,
    left(coalesce(meta_nickname, split_part(new.email, '@', 1)), 24),
    case when meta_gender in ('male','female') then meta_gender else 'male' end
  )
  on conflict (id) do nothing;
  return new;
end $$;

create trigger on_auth_user_created after insert on auth.users
for each row execute function handle_new_user();
```

**avatar 存 key 不存 URL**（D23）：内置头像打进安装包，`avatar-boy` / `avatar-girl` 两个 key，
渲染时映射到 `src/renderer/src/assets/avatars/`。好处是不占 Storage、不产生出口流量，
也不给用户开放上传（没有 Storage 写权限的风险）。`avatar` 为 null 时按 `gender` 回落。

> **2026-11-01 追加**：`invited_by / invited_at / invite_code / deleted_at / deleted_by / deleted_reason`
> 六个字段见 **§10.1**（D28 归属管理 / D30 已停用）。本节 DDL 保持历史原样，不要在这里改。

## 2. 触发器（客户端无法绕过）

```sql
-- 强制 pending，忽略客户端传值
create or replace function force_comment_pending() returns trigger
language plpgsql as $$
begin
  new.status      := 'pending';
  new.user_id     := auth.uid();
  new.created_at  := now();
  new.reviewed_by := null;
  new.reviewed_at := null;
  new.review_note := null;
  new.deleted_at  := null;
  return new;
end $$;

create trigger trg_comment_pending before insert on comments
for each row execute function force_comment_pending();

-- 频率限制（pending 也计入，防止刷队列）
create or replace function check_comment_rate() returns trigger
language plpgsql as $$
begin
  if (select count(*) from comments
      where user_id = new.user_id and created_at > now() - interval '1 minute') >= 1 then
    raise exception 'RATE_LIMIT_MINUTE';
  end if;
  if (select count(*) from comments
      where user_id = new.user_id and created_at > now() - interval '1 day') >= 20 then
    raise exception 'RATE_LIMIT_DAY';
  end if;
  return new;
end $$;

create trigger trg_comment_rate before insert on comments
for each row execute function check_comment_rate();
```

## 3. RLS 策略

```sql
create or replace function is_admin() returns boolean
language sql security definer stable set search_path = public as $$
  select exists (select 1 from profiles where id = auth.uid() and role = 'admin');
$$;

-- ── 参考数据：登录用户只读，管理员可写 ──
alter table balls        enable row level security;
alter table advanced     enable row level security;
alter table display_dict enable row level security;
alter table dataset_meta enable row level security;
alter table profiles     enable row level security;
alter table comments     enable row level security;

create policy balls_read    on balls        for select using (auth.role() = 'authenticated');
create policy balls_write   on balls        for all    using (is_admin()) with check (is_admin());
create policy adv_read      on advanced     for select using (auth.role() = 'authenticated');
create policy adv_write     on advanced     for all    using (is_admin()) with check (is_admin());
create policy dict_read     on display_dict for select using (auth.role() = 'authenticated');
create policy meta_read     on dataset_meta for select using (auth.role() = 'authenticated');

create policy p_read   on profiles for select using (auth.role() = 'authenticated');
create policy p_update on profiles for update using (id = auth.uid());

-- ── 评论：核心是这条读策略 ──
create policy c_read on comments for select using (
  deleted_at is null and (
    status = 'visible'          -- 公开区
    or user_id = auth.uid()     -- 自己的（含 pending / rejected）
    or is_admin()               -- 管理员看全部
  )
);
create policy c_insert on comments for insert with check (user_id = auth.uid());
-- 不给 update / delete 策略：审核走 RPC，删除由管理员在 Dashboard 操作
```

> ⚠️ **上面是 003 的初版骨架，已被后续 migration 覆盖，实际以 `supabase/migrations/` 为准。**
> 读策略的现状见下面「3.1 匿名读」。

### 3.1 匿名读（D22，migration 017）

未登录也能看教学数据，但**只能看已发布的**。所有读策略改成 `to anon, authenticated`，USING 条件一字未改：

| 表 / RPC | anon 能拿到什么 | 为什么安全 |
|---|---|---|
| `balls` / `advanced` | 只有 `state = 1 and review_status = 'visible'` | 条件里的 `owner_id = auth.uid()` 对 anon 恒为 `null`（不成立）、`has_any_role()` 恒 `false`，待审/驳回的行被自然过滤 |
| `comments` | 只有 `status = 'visible'` 且未删除 | 同上，`user_id = auth.uid()` 与 `is_admin()` 对 anon 无效 |
| `display_dict` / `dataset_meta` | 全表 | 字典与版本号本身不含敏感信息 |
| `profiles` | 全表（id / nickname / avatar / role / created_at） | 列表页要显示作者昵称；表内**没有邮箱**，邮箱只经 `list_users()` RPC 下发且仅限 authenticated |
| `get_dataset_snapshot()` / `get_dataset_version()` / `get_comment_counts()` | 正常返回 | security definer 内部已过滤 `visible`，匿名拉不到待审数据 |

**写操作一条没放开**：`balls_insert/update`、`adv_insert/update`、`c_insert` 仍是 `to authenticated`；`profiles` 表级 UPDATE 仍被 revoke；角色变更只能走 `set_user_role` RPC。

匿名实测（2026-10-30）：`balls` 122 行、`advanced` 63 行、`display_dict` 21 行、`profiles` 2 行、快照 `version 1`；`rpc('upsert_ball')` → 401，`insert comments` → 401 RLS 拒绝。

### 3.2 Storage 策略（migration 009 + 018）

| 操作 | 策略 | 说明 |
|---|---|---|
| 读图片 | **不经过 RLS** | bucket `images` 是 public，走 `/storage/v1/object/public/images/<path>` |
| 上传 / 覆盖 / 删除 | `to authenticated` + `can_write_records()` | 高级用户及以上；文件名是 uuid，不会互相覆盖 |
| `select`（对象行） | `images_read`：`to authenticated`（**018 新增**） | 没有这条，`storage.remove()` 会"删 0 行但返回成功"——DELETE 需要先按 RLS 找到目标行 |

> ⚠️ **踩过的坑（T3.3）**：`storage.from('images').remove([...])` 返回 `[]`、无 error，但文件一个没删。原因就是缺 `select` 策略：bucket public 让"读文件"绕过了 RLS，所以 009 从来没建过 select 策略；而 DELETE 走的是 RLS 路径，查不到行 ⇒ 删不到东西 ⇒ 仍然成功返回。**表单保存失败时的图片回滚一度完全无效**。加 018 后实测 6 个测试文件全部删掉。

### 4.1 快照

```sql
create or replace function get_dataset_version() returns int
language sql security definer stable as $$
  select version from dataset_meta where id = 1;
$$;

create or replace function get_dataset_snapshot() returns jsonb
language sql security definer stable as $$
  select jsonb_build_object(
    'version',  (select version from dataset_meta where id = 1),
    'balls',    coalesce((select jsonb_agg(to_jsonb(b) order by b.updated_at)
                            from balls b where b.state = 1), '[]'::jsonb),
    'advanced', coalesce((select jsonb_agg(to_jsonb(a) order by a.updated_at)
                            from advanced a where a.state = 1), '[]'::jsonb),
    'dict',     coalesce((select jsonb_agg(to_jsonb(d) order by d.kind, d.sort)
                            from display_dict d), '[]'::jsonb)
  );
$$;

grant execute on function get_dataset_version()  to authenticated;
grant execute on function get_dataset_snapshot() to authenticated;
```

### 4.2 写入（乐观并发）

```sql
create or replace function upsert_ball(p jsonb, expected_version int)
returns jsonb language plpgsql security definer as $$
declare cur int; new_id uuid;
begin
  if not is_admin() then raise exception 'FORBIDDEN'; end if;

  select version into cur from dataset_meta where id = 1;
  if expected_version is not null and cur <> expected_version then
    raise exception 'VERSION_CONFLICT';
  end if;

  new_id := coalesce(nullif(p->>'id','')::uuid, gen_random_uuid());

  insert into balls (id, color_code, pocket_code, method, strength_code, sight,
                     low_comp, high_comp, remark, impact_image, blue_image, route_image,
                     state, updated_at, updated_by)
  values (new_id, p->>'color_code', p->>'pocket_code', p->>'method', p->>'strength_code',
          p->>'sight', p->>'low_comp', p->>'high_comp', p->>'remark',
          p->>'impact_image', p->>'blue_image', p->>'route_image',
          1, now(), (select nickname from profiles where id = auth.uid()))
  on conflict (id) do update set
    color_code    = excluded.color_code,
    pocket_code   = excluded.pocket_code,
    method        = excluded.method,
    strength_code = excluded.strength_code,
    sight         = excluded.sight,
    low_comp      = excluded.low_comp,
    high_comp     = excluded.high_comp,
    remark        = excluded.remark,
    impact_image  = excluded.impact_image,
    blue_image    = excluded.blue_image,
    route_image   = excluded.route_image,
    state         = 1,
    updated_at    = now(),
    updated_by    = excluded.updated_by;

  return jsonb_build_object('id', new_id,
                            'version', (select version from dataset_meta where id = 1));
end $$;
```

> `delete_ball` / `upsert_advanced` / `delete_advanced` 结构相同：先 `is_admin()`，再校验 version，然后 `update ... set state = 0`。

### 4.3 审核

```sql
create or replace function review_comment(p_id uuid, p_decision text, p_note text default null)
returns void language plpgsql security definer as $$
begin
  if not is_admin() then raise exception 'FORBIDDEN'; end if;
  if p_decision not in ('visible','rejected') then raise exception 'BAD_DECISION'; end if;

  update comments
     set status = p_decision, reviewed_by = auth.uid(), reviewed_at = now(), review_note = p_note
   where id = p_id and status = 'pending';
end $$;

grant execute on function review_comment(uuid, text, text) to authenticated;
```

### 4.4 评论数

```sql
create or replace function get_comment_counts(p_type text, p_ids uuid[])
returns table (target_id uuid, cnt bigint)
language sql security definer stable as $$
  select c.target_id, count(*)
    from comments c
   where c.status = 'visible' and c.deleted_at is null
     and c.target_type = p_type and c.target_id = any(p_ids)
   group by c.target_id;
$$;

grant execute on function get_comment_counts(text, uuid[]) to authenticated;
```

### 5.5 错误码映射

PostgREST 会把 `raise exception 'XXX'` 的 message 原样返回，客户端按此映射：

| 服务端 message | 客户端提示 |
|---|---|
| `FORBIDDEN` | 无权限执行此操作 |
| `VERSION_CONFLICT` | 数据已更新，请刷新后重试 |
| `RATE_LIMIT_MINUTE` | 发得太快了，请稍后再试 |
| `RATE_LIMIT_DAY` | 今天评论太多了，明天再来 |
| `BAD_DECISION` | 非法操作 |
| `BAD_TYPE` | 非法操作（审核目标类型错误） |
| `BAD_ROLE` | 非法操作（不允许设成这个角色） |
| `NOT_PENDING` | 该记录已审核过，请刷新 |
| `USER_NOT_FOUND` | 用户不存在 |

> PostgREST 统一用 **HTTP 400 + `code: P0001`** 返回 `raise exception`，所以要按 `message` 而不是状态码区分。

### 5.6 图片加载（T5.1，2026-11-03）

库里存的是 Storage 相对路径（`balls/<uuid>.webp`），**客户端不直连 Supabase Storage**：

```
snooker-media://media/balls/<uuid>.webp
   ↓ 主进程 protocol.handle（src/main/media.ts）
本地 <userData>/media-cache/<sha1(相对路径)>.<ext>
   ├─ 命中 → 直接返回文件（不发网络请求）
   └─ 未命中 → net.fetch 公共桶 → 原子落盘 → 返回
```

| 约定 | 说明 |
|---|---|
| scheme / host | `snooker-media://media/...`，host 固定 `media`，其余是 Storage 相对路径 |
| 缓存 key | 相对路径的 **SHA-1**（文件名 `<sha1>.webp`），不做反向映射 |
| 落盘 | `tmp + fsync + rename`（铁律 10）；非 2xx / 空 body / > 5 MB **不写** |
| 并发 | 同一路径并发请求只下载一次（主进程 `inflight` 去重） |
| 淘汰 | **不做**。全量 6.7 MB，LRU 是过度设计 |
| CSP | `index.html` 的 `img-src` 必须含 `snooker-media:`，漏了整站图片全破 |
| 环境变量 | 主进程读 `VITE_SUPABASE_URL`，靠 `electron.vite.config.ts` 的 `envPrefix` 注入 |

> 渲染层只用 `imageUrl()`（`src/shared/media/url.ts`）拼地址，不感知缓存；完整 `http(s)://` 原样返回。
> 注意 `connect-src` **没有**放行 `snooker-media:` —— 渲染层不要 `fetch()` 这个 scheme（`<img>` 不受影响），需要二进制就用 `Image`。

## 8. 实现与本文档的差异（T0.2 已落地，2026-10-28）

> 本节记录 migration 实际执行时对第 1–4 节做的**必要修正**。schema 真相仍以 `supabase/migrations/` 为准（D17）。
> 表结构、字段、RLS 策略语义、RPC 签名**均未改动**，下列全部是函数属性与授权层面的加固。

| # | 位置 | 文档原样 | 实际实现 | 原因 |
|---|---|---|---|---|
| 1 | `bump_dataset_version` | 普通 plpgsql | `security definer` | `dataset_meta` 开了 RLS 且无写策略。普通函数在管理员绕过 RPC 直接 `PATCH /balls` 时会以 `authenticated` 身份更新 `dataset_meta` 被拒，导致整条 update 失败 |
| 2 | `check_comment_rate` | 普通 plpgsql | `security definer` | 需统计该用户**全部**评论（含 rejected/已删），非 definer 会被 RLS 过滤掉，限流形同虚设 |
| 3 | 全部 `security definer` 函数 | 部分未写 `search_path` | 统一 `set search_path = public` | 防 search_path 注入，同时消掉 advisor 的 `function_search_path_mutable` |
| 4 | `p_update on profiles` | 只有 `using (id = auth.uid())` | 新增 `guard_profile_role` 触发器 + 显式 `with check` | **原策略允许普通用户把自己 `role` 改成 `admin`**（PostgREST 可直接 PATCH 自己的行），先审后发链路会被绕过。触发器在「有登录身份且非管理员」时把 `role` 回滚为原值；服务端上下文（`auth.uid()` 为 null，如 SQL Editor / service_role）放行，否则永远产生不了第一个管理员 |
| 5 | 函数授权 | 只 grant 了 3 个 | 9 个函数显式 `revoke ... from public, anon` 再 `grant ... to authenticated` | `create function` 默认 `grant execute to public`，不 revoke 的话未登录就能 `POST /rest/v1/rpc/get_dataset_snapshot` 拉走全量数据 |
| 6 | 触发器函数授权 | 未提 | 4 个触发器函数 `revoke from public, anon, authenticated` | 它们被 PostgREST 暴露成 `/rest/v1/rpc/<name>`，属噪音（直接调用会报 "trigger functions can only be called as triggers"）。触发器执行不检查 EXECUTE 权限，revoke 无副作用 |

### 9.3 权限函数（替代原来的单一 `is_admin()`）

```sql
-- 当前用户角色；未登录返回 'anon'
create or replace function current_role_code() returns text
language sql security definer stable set search_path = public as $$
  select coalesce((select role from profiles where id = auth.uid()), 'anon');
$$;

-- 角色判定（数组参数，RLS 里好用）
create or replace function has_any_role(roles text[]) returns boolean
language sql security definer stable set search_path = public as $$
  select coalesce((select role = any(roles) from profiles where id = auth.uid()), false);
$$;

-- 兼容旧调用点：语义升级为「管理员或超管」
create or replace function is_admin() returns boolean
language sql security definer stable set search_path = public as $$
  select has_any_role(array['admin','superadmin']);
$$;

language sql security definer stable set search_path = public as $$
  select has_any_role(array['superadmin']);
```

### 9.4 RLS 重写（`balls` / `advanced` 同构）

```sql
-- 读：可见的 + 自己的（含待审）+ 管理员/超管看全部
drop policy if exists balls_read on balls;
create policy balls_read on balls for select using (
  auth.role() = 'authenticated' and (
    (state = 1 and review_status = 'visible')
    or owner_id = auth.uid()
    or has_any_role(array['admin','superadmin'])
  )
);

-- 插入：高级/管理员，且只能以自己为 owner
drop policy if exists balls_write on balls;
create policy balls_insert on balls for insert
  with check (can_write_records() and owner_id = auth.uid());

-- 更新：只能改自己的
create policy balls_update on balls for update
  using (can_write_records() and owner_id = auth.uid())
  with check (can_write_records() and owner_id = auth.uid());

-- 不给 delete 策略：删除走 RPC 软删（state=0）
```

`storage.objects` 的写策略从 `is_admin()` 改为 `can_write_records()`——高级用户新增记录要能传图。

`profiles` 的读策略保持「登录用户可读」（昵称、角色要公开展示）；**邮箱不放进 profiles**，通过 `list_users()` RPC 取，避免全员可见。

#### 9.4.1 `force_record_review` 触发器（必须，别省）

`review_status` 有默认值 `'visible'`，高级用户绕过 RPC 直接 `POST /balls` 并带上 `review_status='visible'` 就能跳过审核。
所以用 BEFORE INSERT/UPDATE 触发器强制覆盖（同评论的 `force_comment_pending`）：

```sql
create or replace function force_record_review() returns trigger
language plpgsql security definer set search_path = public as $$
begin
  if tg_op = 'INSERT' then
    new.owner_id := coalesce(new.owner_id, auth.uid());
  end if;

  if auth.uid() is null then
    -- 服务端上下文（SQL Editor / service_role / 迁移）：信任调用方
    if new.review_status is null then new.review_status := 'visible'; end if;
  elsif has_any_role(array['admin']) then
    if new.review_status is null then new.review_status := 'visible'; end if;
  else
    new.review_status := 'pending';
    new.reviewed_by := null; new.reviewed_at := null; new.review_note := null;
  end if;
  return new;
end $$;
```

> ⚠️ **`auth.uid() is null` 这个分支不能漏**。这是第二次踩同一个坑（第一次是 `guard_profile_role`）：
> 服务端上下文没有登录身份，`has_any_role()` 恒 false，会被当成普通用户处理。
> 后果是运维在 SQL 里审核通过一条记录，`RETURNING` 却还是 `pending`。

#### 9.4.2 `profiles` 必须用列级授权

只靠 RLS 不够：`p_update` 策略只管「哪一行能改」，不管「改哪一列」。
管理员因此可以 `PATCH` 自己的 profile 把 `role` 改成 `superadmin` 直接提权。

```sql
revoke update on profiles from anon, authenticated;
grant  update (nickname, avatar, gender) on profiles to authenticated;  -- gender 由 019 追加
```

角色变更只能走 `set_user_role` RPC（`security definer`，属主身份不受列授权限制）。
实测（2026-11-01）：客户端 `update({ role: 'admin' })` → `permission denied for table profiles`（42501），
同一行改 `nickname` 正常成功。

### 9.6 版本 bump 条件收窄

`bump_dataset_version` 现在对 `balls` / `advanced` 的**每次 insert/update** 都 +1。加了审核后必须收窄，否则高级用户提交一条待审记录会让所有客户端白下一次快照：

```sql

create trigger trg_balls_changed after insert or update on balls
for each row
when ( (new.state = 1 and new.review_status = 'visible')
    or (old.state = 1 and old.review_status = 'visible') )
execute function bump_dataset_version();
```

含义：只有「曾经可见」或「现在可见」的行发生变化才 bump。纯 `pending` 的提交不 bump。

### 10.2 `handle_new_user` 改造（强制校验邀请码）

```sql
create or replace function handle_new_user() returns trigger
language plpgsql security definer set search_path = public as $$
declare
  meta_nickname text;
  meta_gender   text;
  meta_code     text;
  code_row      invite_codes;
begin
  meta_nickname := nullif(btrim(coalesce(new.raw_user_meta_data->>'nickname', '')), '');
  meta_gender   := new.raw_user_meta_data->>'gender';
  meta_code     := nullif(btrim(coalesce(new.raw_user_meta_data->>'invite_code', '')), '');

  if meta_code is null then
    raise exception 'INVITE_CODE_REQUIRED';
  end if;

  select * into code_row
    from invite_codes
   where code = meta_code and disabled_at is null;
  if not found then
    raise exception 'INVITE_CODE_INVALID';
  end if;

  insert into profiles (id, nickname, gender, invited_by, invited_at, invite_code)
  values (
    new.id,
    left(coalesce(meta_nickname, split_part(new.email, '@', 1)), 24),
    case when meta_gender in ('male','female') then meta_gender else 'male' end,
    code_row.inviter_id,
    now(),
    meta_code
  )
  on conflict (id) do nothing;
  return new;
end $$;
```

**两条硬约束**：

1. **只信 `invite_code`，忽略 metadata 里的 `invited_by` / `role`** —— 否则注册时塞一个 `invited_by: <超管 id>` 就绕过了归属。
2. **`RAISE EXCEPTION` 会让整个 `auth.users` 插入回滚**，所以校验失败 = 用户建不出来。这是唯一的强制点（GoTrue 没有注册前钩子，D27）。

> **实测结论（2026-11-01，T2.6 / T3.9）**：分两条链路，表现不一样 ——
> - **REST 直连** `/auth/v1/signup`：HTTP 500 + `{"code":"P0001","message":"INVITE_CODE_REQUIRED"}`，token 透得出来
> - **supabase-js 的 `signUp()`**：500 被包装成 `Database error saving new user`，**token 丢了**
>
> 所以客户端必须做两件事：① 提交前用 `validate_invite_code()` 预校验（即时反馈）；
> ② 收到 `Database error saving new user` 时**再问一次邀请码**，把原因还原成中文
> （`shared/api/invite.ts` 的 `explainSignUpFailure()`）。

### 10.3 权限函数

```sql
-- ① 已停用账号一律当 anon（否则"停用"只是客户端登出，直接调 API 照样能写）
create or replace function current_role_code() returns text
language sql security definer stable set search_path = public as $$
  select coalesce(
    (select role from profiles where id = auth.uid() and deleted_at is null), 'anon');
$$;

create or replace function has_any_role(roles text[]) returns boolean
language sql security definer stable set search_path = public as $$
  select coalesce(
    (select role = any(roles) from profiles where id = auth.uid() and deleted_at is null), false);
$$;

-- ② 审核归属：能不能审这个人写的东西
create or replace function can_review_owner(p_owner uuid) returns boolean
language sql security definer stable set search_path = public as $$
  select case
    when p_owner is null          then false
    when p_owner = auth.uid()     then true          -- 自己的记录（管理员免审、本人可见）
    when is_superadmin()          then exists (      -- 超管：只审"直邀"（含历史账号 invited_by is null）
      select 1 from profiles where id = p_owner and invited_by is null)
    when has_any_role(array['admin']) then exists (  -- 管理员：只审自己邀请的
      select 1 from profiles where id = p_owner and invited_by = auth.uid())
    else false
  end;
$$;

-- ③ 管理范围：能不能对这个人做用户管理（改角色 / 停用 / 恢复）
create or replace function can_manage_user(p_target uuid) returns boolean
language sql security definer stable set search_path = public as $$
  select case
    when p_target is null or p_target = auth.uid() then false   -- 不能管自己
    when is_superadmin() then exists (
      select 1 from profiles where id = p_target and role <> 'superadmin')
    when has_any_role(array['admin']) then exists (
      select 1 from profiles
       where id = p_target and invited_by = auth.uid()
         and role in ('viewer','advanced'))
    else false
  end;
$$;
```

> `can_manage_user` 里 `role <> 'superadmin'` / `role in ('viewer','advanced')` 就是权限矩阵的硬边界：
> admin 碰不到其他 admin，谁都碰不到超管，谁都不能动自己。

### 10.4 RLS 重写

```sql

drop policy if exists balls_read on balls;
create policy balls_read on balls for select to anon, authenticated using (
  (state = 1 and review_status = 'visible')
  or (auth.uid() is not null and (
        owner_id = auth.uid()
        or can_review_owner(owner_id)

-- advanced 同构

-- ── 评论 ──
drop policy if exists c_read on comments;
create policy c_read on comments for select to anon, authenticated using (
  deleted_at is null and (
    status = 'visible'
    or (auth.uid() is not null and (
          user_id = auth.uid()

  )
);

-- ── profiles：收紧到"自己 + 自己邀请的 + 超管" ──
drop policy if exists p_read on profiles;
create policy p_read on profiles for select to authenticated using (
  id = auth.uid()
  or invited_by = auth.uid()
  or is_superadmin()
);
-- anon 不再能读 profiles（作者昵称改走快照 / RPC）

```

## 11. 站点文案（D31，migration 024）

> 首页等静态文案不再写死在代码里，改由超管在线编辑。
> **走快照下发**，所以离线也能显示；改完 bump `dataset_version`，客户端下次启动自动更新。

### 11.1 表结构

```sql
create table site_sections (
  key        text primary key,          -- 'home:statement' / 'home:custom-xxx'
  page       text not null default 'home',  -- 预留：以后关于页、小键盘说明复用同一套
  title      text not null,             -- 1~40 字
  intro      text,                      -- 可选，≤200 字
  sort       int  not null default 0,
  updated_at timestamptz not null default now()
);

create table site_points (
  id          uuid primary key default gen_random_uuid(),
  section_key text not null references site_sections(key) on delete cascade,
  label       text,                     -- 可选，≤12 字（渲染成小胶囊）
  body        text not null,            -- 1~500 字（列名不用 text，避免和类型名混淆）
  sort        int  not null default 0,
  updated_at  timestamptz not null default now()
);
```

**为什么两张表而不是一个 jsonb 大字段**：单条编辑不用整篇覆盖；以后要做"只改一条"的接口也不用改表结构。

### 11.2 RLS

```sql
alter table site_sections enable row level security;
alter table site_points   enable row level security;

create policy ss_read on site_sections for select to anon, authenticated using (true);
create policy sp_read on site_points   for select to anon, authenticated using (true);
-- 不给 insert / update / delete 策略：写只走 RPC
```

文案是公开内容，**匿名也能读**（和 D22 一致，未登录也能看首页）。

### 11.3 RPC

| 函数 | 权限 | 行为 |
|---|---|---|
| `save_site_section(p_section jsonb)` | **仅超管** | 按 `key` upsert 分组，**整组覆盖**条目（先删后插，按数组顺序写 `sort`）；空 `body` 跳过；bump 版本 |
| `delete_site_section(p_key text)` | **仅超管** | 删分组（条目级联）；bump 版本 |

`p_section` 形如 `{ key, page?, title, intro?, sort?, points: [{ label?, body }] }`。

**为什么整组覆盖**：编辑页是"改一组 → 保存这一组"，覆盖比逐条 diff 简单，也不会出现"删了条目但服务端还留着"的半截状态。代价是**保存一次会 bump 一次版本**（`保存全部` 保存 N 组就是 N 次），可以接受。

### 11.4 快照

`get_dataset_snapshot()` 多返回一个 `content` 键：

```json
{ "content": [
  { "key": "home:statement", "title": "声明", "intro": null, "sort": 0,
    "points": [{ "label": "用途", "body": "…" }] }

```

### 11.5 客户端两级来源

| 优先级 | 来源 | 场景 |
|---|---|---|
| ① | 快照 `content` | 正常情况（含离线，用的是上次同步的文案） |
| ② | `content/home.ts` 内置文案 | 首次启动没网 / 旧缓存里没有 `content` 字段 |

### 11.6 编辑入口

`views/ContentView.vue`，路由 `/content`（`meta.roles: ['superadmin']`），菜单在「更多 → 文案管理」。

- 改的是本地草稿，点「保存全部」才提交
- 保存时按卡片顺序写回 `sort`，所以「上移 / 下移」也能调顺序

## 12. 评论接口（T4.1，migration 025）

> 表 / 触发器 / 审核 RPC 在 001~004 就建好了，021 又把读策略收窄到「邀请归属」。
> 025 补的是**客户端真正要用的两个入口**：分页读、发一条。
> 评论**不进快照**（铁律 6），所以一切都走 RPC 实时查。

### 12.1 为什么读也走 RPC，不直接 `select comments`

| 原因 | 说明 |
|---|---|
| 昵称/头像拿不到 | 021 之后 `p_read on profiles` 只剩「自己 + 自己邀请的 + 超管」，评论区里大多是别人邀请的用户。RPC 是 `security definer`，在函数内 join，**不放开 profiles 的整表读权** |
| `author_deleted` 只能算出来 | D30 的「已停用」标识依赖 `profiles.deleted_at`；评论不在快照里，只能随查询返回 |
| 三段可见范围写一次 | 公开区 / 自己的三态 / 有审核权的范围，在 SQL 里一次表达，客户端不用拼查询，也不会漏条件泄露待审评论 |

### 12.2 `list_comments`

```sql
list_comments(p_type text, p_target_id uuid, p_limit int default 20, p_offset int default 0)
returns table (
  id uuid, content text, status text, created_at timestamptz, user_id uuid,
  nickname text, avatar text, gender text, author_deleted boolean,
  review_note text, total bigint
)
```

- 排序：`created_at desc`（最新在上）
- 分页兜底：`p_limit` 缺省 20、上限 100；`p_offset` 负数归零
- 可见范围（与 `c_read` 同构，但**已停用账号当 anon**）：

| 调用者 | 能看到 |
|---|---|
| anon | 只有 `status = 'visible'` |
| 登录用户（未停用） | visible + 自己的 pending/rejected |
| admin | 再加**自己邀请的**账户的 pending/rejected |
| superadmin | 再加 `invited_by is null` 账户的（即"直邀"） |
| 已停用账号 | 与 anon 相同（D30，不会因为 `user_id = auth.uid()` 漏看自己的待审） |

- `review_note`（驳回原因）**只回给自己的评论**，别人的恒为 null —— 避免前台泄露审核口径
- ⚠️ `total` 是**当前调用者可见**的条数，且**这一页为空时返回 0**（窗口函数数不到行）。
  它只用于判断「还有没有下一页」；界面上的「评论 (N)」请用 `get_comment_counts`（只数 visible）

### 12.3 `create_comment`

```sql
create_comment(p_type text, p_target_id uuid, p_content text) returns jsonb  -- {id, status:'pending'}
```

校验顺序（全部在函数里，客户端绕不过）：

1. 未登录 → `AUTH_REQUIRED`
2. `profiles.deleted_at` 非空 → `ACCOUNT_DISABLED`
3. `p_type` 不是 ball/advanced → `BAD_TYPE`
4. 内容 trim 后为空 / 超过 300 → `EMPTY_CONTENT` / `TOO_LONG`
5. 目标不存在、`state <> 1` 或 `review_status <> 'visible'` → `TARGET_NOT_FOUND`
   （**不给待审 / 已隐藏的记录评论**，直接 insert 拦不住这条）
6. 落库时 `trg_comment_pending` 覆盖 `status/user_id/created_at`（铁律 5），
   `trg_comment_rate` 抛 `RATE_LIMIT_MINUTE`（1 分钟 1 条）/ `RATE_LIMIT_DAY`（每天 20 条）

### 12.6 实测（2026-11-02）

测试数据：一条记录上 5 条评论（骑驴 3 条：visible / pending / rejected；酸菜黄花鱼 1 条 pending；超管 1 条 pending），测完全部物理删除（评论不 bump 版本，`dataset_meta.version` 全程停在 38）。

| 身份 | 期望 | 实测 |
|---|---|---|
| anon | 1 条 visible，`total = 1` | ✅ |
| 骑驴（viewer） | 自己的 3 条，别人的 pending 看不到 | ✅ 3 条；`review_note` 只在自己那条 rejected 上有值 |
| 酸菜（admin，骑驴挂在其名下） | 4 条（含骑驴的 pending/rejected） | ✅ |
| 酸菜（撤掉 `invited_by` 后） | 只剩 visible + 自己的 pending | ✅ 2 条 —— 归属范围生效 |
| 超管 | 全部 5 条 | ✅ |
| 骑驴被临时停用 | 当 anon：只见 visible；`author_deleted = true` | ✅ 1 条；别人看它的评论带「已停用」 |
| 被停用账号发评论 | 拒绝 | ✅ `ACCOUNT_DISABLED` |
| `create_comment` 正常 | `pending` + 最新在上 | ✅ |
| 1 分钟内发第二条 | `RATE_LIMIT_MINUTE` | ✅ |
| 空白内容 / 不存在的目标 | `EMPTY_CONTENT` / `TARGET_NOT_FOUND` | ✅ |
| anon 调 `create_comment` | 拒绝 | ✅ HTTP 401 `permission denied for function create_comment` |
| PostgREST 实链路 | anon 拿到 join 后的昵称 | ✅ `nickname: 骑驴`，`author_deleted: false` |

### 12.7 审核队列（T4.3，migration 026）

> `review_comment` 在 021 就按归属收窄好了，缺的是"列出待审"的入口 —— 管理员否则只能盲审。

```sql
list_pending_comments(p_limit int default 50, p_offset int default 0)
returns table (
  id uuid, content text, created_at timestamptz, user_id uuid, nickname text,
  author_deleted boolean, target_type text, target_id uuid,
  target_color text, target_pocket text, target_method text,
  target_title text, target_category text, total bigint
)

count_pending_comments() returns bigint
```

| 项 | 说明 |
|---|---|
| 范围 | 只 `has_any_role(['admin','superadmin'])`；再按 `can_review_owner(user_id)` 过滤（admin 看自己邀请的、超管看直邀的） |
| 排序 | `created_at asc` —— 审核队列先来先审，不是按最新 |
| 为什么要 join | 作者昵称拿不到（021 收紧了 `profiles` 读权）；审核要看"评论挂在哪条记录上"，所以 join `balls` / `advanced` 带回颜色/袋口/方法/标题/系列 |
| 目标信息 | 彩球回 `target_color/pocket/method`，进阶回 `target_title/category`，前端用 `dataset.dictName` 映射成中文，服务端不硬编码中文 |
| 非管理员 | `list_pending_comments` 抛 `FORBIDDEN`；`count_pending_comments` 直接返回 `0`（角标不该报错） |
| 权限 | 两个都只给 `authenticated`，anon 是 `permission denied` |
| 审核后 | 不 bump `dataset_version`（铁律 6）；`023` 的 `audit_comment_review` 触发器自动写 `admin_actions`（`from/to/note`） |

**客户端**：顶部铃铛角标 = `count_pending_comments()`，进页面取一次 + 60 秒轮询（`TopBar.vue`）；点击打开 `CommentReviewDialog.vue`，通过/驳回（驳回原因可选，最多 200 字）。对话框开着时角标数字与列表长度不一致会补一次刷新，避免"角标 1、点进去是空的"。

### 12.8 记录审核队列（T4.5，migration 027）

> 高级用户投稿后 `review_status='pending'`（D21），但此前只有 `review_record` RPC、没有界面 —— 投稿永远进不了公开区。这一节补的是队列。

```sql
list_pending_records(p_limit int default 50, p_offset int default 0)
returns table (
  record_type text, id uuid, color_code text, pocket_code text, method text,
  strength_code text, category_code text, title text, preview jsonb,
  created_at timestamptz, owner_id uuid, nickname text, author_deleted boolean, total bigint
)

count_pending_records() returns bigint
```

| 项 | 说明 |
|---|---|
| 数据来源 | `balls` + `advanced` `union all`，只取 `state = 1 and review_status = 'pending'` |
| 范围 | `can_review_owner(owner_id)`；历史行 `owner_id is null` 的只有超管能审（与 `review_record` 的判定逐条对齐） |
| 排序 | `created_at asc`（先提交先审） |
| **为什么要 `preview`** | 待审记录**不在快照里**，详情页打不开。审核要看的正文必须随队列返回：彩球 `sight / low_comp / high_comp / remark`，进阶 `description / content`。**不回图片路径**（图在 Storage，文字足够判断） |
| 权限 | 只给 `authenticated`；非管理员 `FORBIDDEN` / 计数 0 |

**审核后的副作用（与评论不同）**：

| 内容 | 通过 | 驳回 |
|---|---|---|
| 评论 | 不 bump，客户端下次查询即可见 | 不 bump，`review_note` 回给作者 |
| 记录 | **bump `dataset_version`**（记录在快照里），客户端要 `sync` 才看得到 | 不 bump（`pending → rejected` 两侧都不在快照里） |

**客户端**：`components/ReviewDialog.vue` 的两个页签（评论 / 记录），角标 = `count_pending_comments() + count_pending_records()`。记录通过后调用方要 `dataset.sync(true)`，否则列表页还是旧数据。

### 12.9 审核预览与结果通知（T4.6 / T4.7，migration 028/029）

#### `get_review_record(p_type text, p_id uuid) → jsonb`

按 id 取**单条待审记录整行**（含 `impact_image / blue_image / route_image` 路径）。

| 项 | 说明 |
|---|---|
| 为什么需要 | 待审记录不在快照里，详情页打不开；而打法合格与否要看图，队列里的文字摘要不够 |
| 范围 | 与 `review_record` 完全一致（`can_review_owner`；`owner_id is null` 的只有超管） |
| 返回 | 整行 `to_jsonb`，前端按快照行类型直接用 |
| 前置条件 | 记录必须仍是 `pending`，否则 `NOT_PENDING`（审核完再点会看到这个） |

客户端用法：详情页发现「快照里没有 + 我是管理员」→ 调它 → 进入审核预览模式（顶部审核条 + 完整内容 + 通过/驳回）。

#### `notifications`（审核结果通知）

```sql
create table notifications (
  id uuid pk, user_id uuid, kind text, title text, body text,
  target_type text, target_id uuid, read_at timestamptz, created_at timestamptz
);
```

| 项 | 说明 |
|---|---|
| kind | `comment_visible` / `comment_rejected` / `record_visible` / `record_rejected` |
| 写入 | **只有触发器**：评论 / 记录的 `pending → visible/rejected` 时各落一条（`notify_comment_review` / `notify_record_review`），函数是 `security definer` |
| RLS | 只有 `for select using (user_id = auth.uid())`；**没有 insert/update/delete 策略**，客户端伪造不了，标已读只能走 RPC |
| body | 通过 = 内容摘要（评论前 60 字 / 记录标题）；驳回 = `review_note`，空则「管理员没有填写原因」 |
| target | `target_type` + `target_id` 指向**记录**（评论通知也指向它挂着的记录），点通知跳详情 |
| 快照 | **不进快照、不 bump 版本**（与评论同理） |

| RPC | 权限 | 行为 |
|---|---|---|
| `list_notifications(p_limit, p_offset)` | `authenticated` | 只返回自己的，最新在上，带 `total` |
| `count_unread_notifications()` | `authenticated` | 未读数（顶部角标） |
| `mark_notifications_read(p_ids uuid[] default null)` | `authenticated` | 不传 ids = 全部已读；返回实际更新条数 |

#### 触发器的一个坑（029 修的）

`notify_record_review()` 同时挂在 `balls` 和 `advanced` 上，取标签时**不能用 CASE 选字段**：

```sql
-- ✗ 会报 record "new" has no field "title"（plpgsql 准备语句时把两个分支的字段都解析了）
case tg_table_name when 'balls' then new.method else new.title end

-- ✓ IF 分支是首次执行才准备的，走不到的不会解析
if tg_table_name = 'balls' then ... new.method ... else ... new.title ... end if
```

### 12.10 系统通知与审核人信息（T4.8 / T4.10，migration 030）

#### 表结构变化

| 变化 | 说明 |
|---|---|
| `kind` 加 `'system'` | 系统通知 |
| `target_type` / `target_id` 改为**可空** | 系统通知不指向记录 |
| 新增 `reviewer_id` / `reviewed_at` | 谁审的、什么时候审的（系统通知里是发布人和发布时间） |

#### `publish_system_notice(p_title, p_body) → int`

| 项 | 说明 |
|---|---|
| 权限 | 仅 `superadmin`，否则 `FORBIDDEN` |
| 行为 | **fan-out**：给所有 `deleted_at is null` 的账号各插一条 `kind='system'`，返回收到人数 |
| 长度 | 标题 ≤60（空则 `EMPTY_TITLE`），正文 ≤500（可空） |
| 审计 | 落一条 `admin_actions(action='publish_system_notice', detail={title, recipients})` |
| 为什么 fan-out | 用户上限 100，一次最多 100 行；已读 / 角标 / 列表 / 删除全部复用现成逻辑。代价：新注册用户看不到历史系统通知 |

| `delete_notification(p_id)` | 自己的 | 删一条（系统通知删的是自己那份副本） |
| `clear_read_notifications()` | 自己的 | 删掉自己所有已读通知，返回条数 |

### 12.11 作者侧投稿 / 审核回显 / 角色通知（T4.11~T4.14，migration 031）

#### 作者能看见自己的待审 / 驳回记录

**为什么不放进快照**：快照是公开分发、还会落本地缓存文件。把 `pending`/`rejected` 塞进去会
① 切账号时缓存串数据；② 待审内容可能被匿名请求看到。所以单独两个 RPC：

| RPC | 权限 | 返回 |
|---|---|---|
| `get_my_record(p_type, p_id)` | 作者本人（`owner = auth.uid()`） | 整行 + `reviewer_name` / `reviewer_role` |
| `list_my_records()` | 同上 | 彩球 + 进阶合并，含 `review_status` / `review_note` / `reviewed_at` / `reviewer_*` |

#### 待审期间锁定编辑

`upsert_ball` / `upsert_advanced` 在"改已有记录"分支多了一条：

```sql
if v_status = 'pending' then raise exception 'PENDING_LOCKED'; end if;
```

- 只在前端隐藏「编辑」按钮不算锁，绕过 UI 直接调 RPC 照样能改
- 驳回（`rejected`）不锁：作者改完保存会走 `force_record_review` 重新变 `pending`，等于"重新提交审核"

#### 删除记录 → 同步清通知

`clear_record_notifications` 触发器（`balls` / `advanced` 的 `after update`）：

```sql
if new.state = 0 and old.state <> 0 then
  delete from notifications where target_id = new.id;
end if;
```

用触发器而不是在 `delete_ball` 里删，是为了同时覆盖"运维直接改库"的情况。

#### 审核回显

统一格式：`由 管理员 张三 审核 · 2026-11-02 21:21 [已通过]`

| 位置 | 数据来源 | 可见性 |
|---|---|---|
| 评论 | `list_comments` 的 `reviewer_name` / `reviewer_role` / `reviewed_at` | 只给 `c.user_id = auth.uid()`，别人是 null |
| 记录详情（作者看自己） | `get_my_record` 拼上的 `reviewer_name` / `reviewer_role` | 只有作者能调 |
| 我的投稿列表 | `list_my_records` | 同上 |
| 通知 | `list_notifications` join `profiles` | 通知只回给本人 |

前端组件 `components/ReviewStamp.vue` 统一渲染，避免三处各写一遍。

#### 角色变更通知（T4.14）

`profiles.role` 变化时 `notify_role_changed` 触发器落一条 `kind='role_changed'`：

- 标题「你的账户角色已更新」，正文「现在是「高级用户」，请重启程序后生效」
- 归到**系统类**（`scope='system'` 含 `system` + `role_changed`）
- 为什么提示重启：客户端在启动时把角色换算成 `canWrite` / `isAdmin`，改完不重启界面不会变

#### 通知计数

`notification_counts() → { all, system, unread }`：弹窗三个页签标题上的数字用 `all` / `system`，
未读数仍然只用于顶栏角标。
