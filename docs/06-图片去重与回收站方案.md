## 1. 这份文档解决什么

| 编号 | 需求 | 一句话 |
|---|---|---|
| **R1** | 图片去重上传 | 同一份文件资源在 Storage 里只存一份，不因重复上传占桶 |
| **R2** | 回收站（超管） | 列出所有**已软删除**的记录，可**恢复**或**物理删除** |
| **R3** | 孤儿图清理 | 扫描桶里**没有任何记录引用**的图片，超管确认后删除；入口放在回收站页面 |

三条需求的共同目标：**桶里的对象 = 数据真正需要的对象**，不多不少。

## 3. 明确不做的事（附理由，避免以后又被翻出来）

| 不做 | 理由 |
|---|---|
| **驳回时删图** | 驳回 = "改改再来"，记录和图片都要留着。作者从「我的投稿」进详情改稿，第一件事就是加载这张图 |
| **删除记录时同步删图** | 软删除的行仍持有路径，逻辑上算不出孤儿；真要算就得排除本行，那"恢复记录"就必然裂图 |
| **停用账号时删图** | D29 要求恢复账号时还原内容，删图等于把恢复功能废掉 |
| **`image_gc_queue` 延迟队列** | 100 人 / 22 KB 一张的规模，回收靠人工触发的一次性对账就够，队列是过度设计 |
| **`image_assets` 登记表（存量老图去重）** | 收益上限 6.93 MB（328 张全被重传一次），成本是一个表 + 回填 + 每次上传多一次查询。等内容量涨上来再说 |
| **让客户端自己算引用 / 自己拼删除列表** | RLS 让普通用户看不到别人的 `pending`/`rejected` 记录，会把共享图误判成孤儿 |

## 4. R1 · 图片去重上传

### 4.1 核心机制

**路径由内容决定**，同一份字节永远算出同一个路径，于是"是否已存在"不需要查表：

```
path = <dir>/<sha256(WebP 字节)>.webp
```

- `dir` 保持 `balls` / `advanced`（与历史数据一致，便于按类型看桶内容）
- hash 的是**转码后的 WebP 字节**，不是原始 PNG —— 库里存的就是 WebP，只有对"要存进去的那份字节"做 hash，才能保证内容相同 → 路径相同
- 不复用缓存那套 SHA-1（那是"路径 → 文件名"的 key，两套命名空间不能混）

### 4.2 数据流

```
用户选图
  ↓ toWebp(file)                       现有逻辑不动
  ↓ sha256Hex(blob)                    crypto.subtle.digest，22 KB < 5 ms
path = balls/<hash>.webp
  ↓ HEAD 公共 URL（无 body，~30 ms）
  ├─ 200 → 已存在，直接引用     → { path, created: false }
  └─ 404 → upload(upsert:false)
            ├─ 成功            → { path, created: true }
            └─ 409 已存在       → { path, created: false }（并发抢先）
```

### 4.3 改动点

| 文件 | 改动 |
|---|---|
| `src/shared/media/upload.ts` | 新增 `sha256Hex()`；`uploadImage()` 返回 `{ path, created }`；HEAD 探测；409 视为成功 |
| `components/BallFormDialog.vue` | 收集结果，只把 `created === true` 的路径放进回滚列表 |
| `components/AdvancedFormDialog.vue` | 同上 |

后端**零改动**：桶是 public（HEAD 可匿名），insert 策略已是 `can_write_records()`，`upsert:false` 已是现状。

### 4.4 回滚语义必须一起改（这是真正的坑）

现有逻辑：保存失败 → `removeUploadedImages(刚传的路径)`。

去重之后，如果删的是"命中已有"的路径，**会把别人正在用的图删掉**，那条记录当场裂图。而 Storage 的 delete 策略是 `can_write_records()`，高级用户能删任意对象，没有兜底。

规则：**回滚只删 `created === true` 的路径**。

残余风险（可接受）：两台设备几乎同时传同一张新图，A 拿到 `created:true`、B 拿到 409；此时 A 保存失败并回滚，会把 B 刚引用的对象删掉。窗口是秒级、概率极低，暂不做引用校验（真要做就是 4.7 里的"删前再查一次"）。

### 4.5 边界与失败模式

| 情况 | 行为 |
|---|---|
| 同一张图在一个表单里被选两次（如击球点 + 蓝点） | 第二次 HEAD 命中 → 同一 path，两个字段共用 |
| 两台设备/两个账号传同一张图 | 同一 path，桶里一份 |
| 同一张图另存为不同格式/尺寸 | 字节不同 → 不同 path，各存一份（**不做感知哈希**，宁可多存不可错引用） |
| hash 计算失败 / 浏览器不支持 `crypto.subtle` | 回退到 `randomUUID()` 命名（保证上传不失败） |
| 409 判定 | 按 `statusCode === '409'` 判断，**不要匹配 message 文案**（会变） |

### 4.6 存量 328 张老图

老图是 `balls/<uuid>.webp`，算不出 hash 路径 → 用户重新选老图的原始文件时会多存一份。最坏 328 张 / 6.93 MB（桶的 0.7%），一次性上限，**本期不处理**。

### 4.7 验收

1. 同一张图连传两次 → 桶里只有一份、两条记录同一路径，第二次 `created:false`
2. 保存失败回滚 → 只删本次新建的，命中已有的那张还在，其他记录不裂图
3. 不同图片 → 路径不同、互不影响
4. 同一表单里两个字段选同一张图 → 两个字段同一路径，桶里一份

## 5. R2 · 回收站（超管）

### 5.1 权限与可见范围

- **只有 `superadmin`**（用户明确要求"管理所有已软删除记录"）。admin 的边界是"自己邀请的人"，回收站跨邀请人，不给。
- 页面入口：「更多 → 回收站」，仅超管可见（与「文案管理」同级）。

### 5.2 数据口径（什么算"已软删除"）

| 条件 | 归类 | 是否进回收站 |
|---|---|---|
| `state = 0` 且 `hidden_reason is null` | 作者主动删除 | ✅ 列表展示，可恢复、可物理删除 |
| `state = 0` 且 `hidden_reason = 'owner_deleted'` | 账号停用级联隐藏 | ❌ **不展示**（已确认）：这类内容由「账户管理 → 恢复账号」统一还原，混进回收站会诱导超管单独恢复，破坏 D29 的还原链路 |
| `review_status = 'rejected'` 且 `state = 1` | 审核驳回 | ❌ 记录还活着，作者要改稿重提 |
| `review_status = 'pending'` | 待审 | ❌ 不进回收站 |

> 因此页面**只有一栏**：`state = 0 and hidden_reason is null`。
> 恢复时仍要兜底校验作者状态（见 5.5）—— 作者可能在记录被删之后才被停用。

### 5.3 页面结构

```
回收站（仅超管）
├─ 筛选：类型（彩球 / 进阶）、彩球颜色、删除时间范围
├─ 列表：缩略图 · 标题 · 作者 · 删除时间 · 图片数 · 状态标签
├─ 行操作：恢复 / 物理删除
└─ 底部区块：孤儿图片清理（见 R3）
```

缩略图直接用 `LazyImage`（图片走 `snooker-media://`，已缓存的不再下载）。

### 5.4 RPC 设计

```sql
-- 列表
list_deleted_records(p_type text default null,   -- 'ball' | 'advanced' | null
                     p_limit int default 50, p_offset int default 0)
returns table (
  rec_type text, id uuid, title text,
  owner_id uuid, owner_nickname text, owner_deleted boolean,
  color_code text, pocket_code text, category_code text,
  review_status text,
  deleted_at timestamptz,          -- 用 updated_at 近似（删除时会更新）
  image_paths text[], image_count int,
  total_count bigint               -- 分页用
)
-- 权限：is_superadmin()
-- 过滤：state = 0 and hidden_reason is null

-- 恢复
restore_record(p_type text, p_id uuid) returns void
-- 校验：超管；行存在且 state = 0
-- 若 hidden_reason = 'owner_deleted' 且 owner 的 profiles.deleted_at 不为空 → raise OWNER_DISABLED
-- update state = 1, hidden_reason = null, updated_at = now()
-- balls/advanced 的 trigger 自动 bump dataset_version（update 事件）

-- 物理删除
purge_record(p_type text, p_id uuid) returns text[]
-- 权限：超管；行必须 state = 0（防止从别处误删在用记录）
-- 1) 审计快照：insert into admin_audit_log(action='purge_record', actor_id, target_type, target_id, payload=to_jsonb(整行))
-- 2) delete from comments      where target_type = p_type and target_id = p_id
-- 3) delete from notifications where target_type = p_type and target_id = p_id
-- 4) delete from balls/advanced where id = p_id and state = 0
-- 5) 显式 bump dataset_version（delete 不在触发器覆盖范围）
-- 6) 返回"删完之后变成孤儿"的图片路径（交给 R3 或直接提示）
```

**审计表**：**复用 023 已有的 `admin_actions`**（`action='purge_record'`，`detail` 里存整行快照），不再新建 `admin_audit_log` —— 项目里已经有一张只给超管读、只允许 security definer 写入的审计表，再建一张只会让"谁干了什么"分散在两处。

```sql
-- 023 已存在，这里只是复用，不新建
admin_actions (
  id uuid, actor_id uuid, action text, target_id uuid, detail jsonb, created_at timestamptz
)
-- 物理删除写入：action='purge_record', detail={ type, row: to_jsonb(整行) }
```

### 5.5 恢复的约束

- 恢复前校验作者状态：作者仍停用 → 拒绝并提示「请先恢复该账号，再恢复其内容」
- 恢复后 `hidden_reason` 必须清空，否则下次"恢复账号"会重复处理
- 恢复 `state=1` 的记录若原本是 `pending` / `rejected`，**不改 `review_status`**（D29 的同一原则：隐藏与审核是两件事）

### 5.6 物理删除的连带影响

| 对象 | 处理 |
|---|---|
| `comments` | 物理删（多态关联无外键，必须手动） |
| `notifications` | 物理删（同上） |
| `dataset_version` | **显式 bump**（delete 不触发） |
| 快照 | 版本变了，客户端下次启动自动全量同步 |
| 图片 | 不在这里删，进入 R3 的孤儿列表 |

### 5.7 验收

1. 作者删除一条 → 出现在「作者删除」页签，缩略图正常
2. 恢复 → 列表消失、内容页可见、`dataset_version` +1
3. 物理删除 → 行消失、其评论与通知一起消失、`dataset_version` +1、审计表有快照
4. 停用某账号 → 其内容**不出现**在回收站（`hidden_reason='owner_deleted'` 被过滤）
5. 先删记录、后停用作者 → 回收站里该记录点「恢复」被拒，提示「请先恢复该账号」
6. 非超管访问路由 → 菜单不显示、直接输 URL 也进不去（`is_superadmin` 双重校验）

## 6. R3 · 孤儿图清理

### 6.1 判定口径

**桶里有、但没有任何记录引用**的对象：

```sql
-- 引用计数：不分 state、不分 review_status
-- （被软删/驳回/停用的行仍持有路径，它们还要恢复、要改稿）
not exists (select 1 from balls b
            where o.name in (b.impact_image, b.blue_image, b.route_image))
and not exists (select 1 from advanced a where a.image = o.name)
```

**能读 `storage.objects` 的前提**：函数用 `security definer`，属主是 `postgres`，可以直接 select 该表。这是本方案能"对账全桶"的关键 —— 只靠业务表永远扫不出"上传成功但保存失败"的残留。

### 6.2 RPC

```sql
list_orphan_images(p_limit int default 200, p_offset int default 0)
returns table (path text, bytes bigint, created_at timestamptz, total_count bigint)
-- 权限：is_superadmin()
-- 数据源：storage.objects where bucket_id='images'
-- 体积：metadata->>'size'
```

### 6.3 删除执行

- **客户端调 `storage.remove(paths)`**（Storage 对象不能从 SQL 删），每次 ≤ 50 个分批
- 只删服务端返回的路径，**客户端不自己拼**
- 删除前弹确认：`将删除 N 张图片（X MB），此操作不可撤销`
- 删完重新拉一次列表刷新

### 6.4 安全边界

| 风险 | 对策 |
|---|---|
| 误删共享图 | 计数在服务端（security definer），客户端看不到别人的 pending/rejected 记录 |
| 竞态（算完孤儿后有人新建引用） | 人工触发 + 二次确认，窗口毫秒级；不做队列（见第 3 节） |
| 越权删除 | `is_superadmin()`；Storage delete 策略本身是 `can_write_records()`，超管满足 |
| 删错不可恢复 | 确认框写明数量与体积；删除动作写 `admin_audit_log`（action='purge_image'，payload 存路径列表） |

### 6.5 与 R2 的联动

物理删除一条记录后，它独占的图片立刻变成孤儿。处理方式：**物理删除成功后自动刷新孤儿列表**，并在提示里写「该记录独占的 3 张图片已进入孤儿列表」，由用户在同一页面一并清理。

### 6.6 验收

1. 手动上传一张图但不保存（模拟残留）→ 孤儿列表能看到它
2. 一条记录被两条数据共享图片 → 删掉其中一条 → 图片**不出现**在孤儿列表
3. 物理删除记录 → 其独占图出现在孤儿列表 → 清理后桶里对象数减少、`admin_audit_log` 有记录
4. 清理后刷新页面 → 列表为空、无残留

## 10. 风险与回滚

| 风险 | 等级 | 缓解 |
|---|---|---|
| 物理删除不可逆 | 高 | 审计表存整行快照；只允许删 `state=0` 的行；二次确认 |
| 误删共享图 | 高 | 服务端计数；客户端只执行服务端列表 |
| 恢复后露出停用账号内容 | 中 | 恢复前校验 `profiles.deleted_at` |
| 去重导致回滚误删 | 中 | `created` 标记；残余竞态已知可接受 |
| 物理删除漏清评论/通知 | 中 | RPC 内按顺序清理；验收专门测 |
| `dataset_version` 漏 bump | 中 | 物理删除后显式 bump（delete 不触发触发器） |

**回滚方案**：代码 `git revert`；数据库写反向 migration（`drop function` / `drop table admin_audit_log`）。已删除的 Storage 对象无法回滚 —— 这是本方案唯一不可逆的点，所以清理入口必须是超管手动触发。
