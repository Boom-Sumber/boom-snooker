# 10 · 应用内更新方案

> 状态：**方案已确认（2026-11-03），尚未实现**。
> 已确认的三项：① 托管用 **Cloudflare R2**（Supabase 只放清单与版本表）② 强制更新**仅在本地版本低于 `min_supported_version`** 时触发 ③ 实现顺序排在 **T6.3 打包之后**、T6.4 之前。
> 关联决策：D2（不做同步引擎）、D12（不用 Edge Function）、D17（DDL 走 migration）、成本红线（`docs/00` §2）。

---

## 1. 为什么安装包不能放 Supabase Storage

T6.3 实测：`snooker-0.1.0-setup.exe` = **132 MB**（138,206,745 B）。对照 Supabase Free：

| 限制 | 官方数值 | 结论 |
|---|---|---|
| 单文件上传上限 | **50 MB**（Pro 才放宽） | 132 MB **传不上去**，压缩到 12% 不可能；裁掉 55 个语言包（49 MB 未压缩）也只到 ~120 MB |
| 月出口流量 | **5 GB**（另有 10 GB = 5 cached + 5 uncached 的口径） | 132 MB × 30 人 = **4 GB**，一次全量发版见底；100 人 = 13 GB。超了会连累图片与快照 |

这两条各自独立致命，**不是配置问题**。因此：

- ❌ 放弃「Supabase Storage 直接放 exe」
- ❌ 放弃「Supabase Storage 分片 + 自研下载器」—— 同样吃 5 GB，还要放弃差分、多写 400+ 行下载器
- ✅ 采用「**Supabase 存 `latest.yml` + 版本表，二进制放 R2**」

## 2. 架构

```
发布机（本地脚本，持 service_role + R2 密钥）
  ├─ npm run build:win → exe / .blockmap / latest.yml
  ├─ 上传 exe + blockmap  →  Cloudflare R2（私有桶，S3 API）
  ├─ 上传 latest.yml      →  Supabase Storage（public 桶 releases/win/）
  └─ 写 app_releases 表   →  Supabase Postgres（service_role）

客户端（几十台）
  ├─ electron-updater  generic provider → Supabase Storage 取 latest.yml
  │                     yml 里 files[].url 写 R2 的绝对地址
  └─ 下载 / 差分 / 校验 sha512 → 退出并静默安装新版本
```

**关键可行性依据**（已读 electron-updater 源码确认）：`util.ts` 的 `newUrlFromBase` 用 `new URL(pathname, baseUrl)`，**清单里的绝对 URL 会被原样保留**，不会被拼到 base 上。所以 latest.yml 与安装包可以分处两个域名，不需要自定义 Provider、不需要 hack。

`latest.yml` 只有 343 B，走 Supabase 的流量可以忽略；渠道文件的 CDN 缓存问题由 electron-updater 自带的 `noCache` 查询参数规避（`isAddNoCacheQuery`）——但**仍需实测** Supabase 对该未知 query 参数返回 200 而非 400。

## 3. 数据模型（`supabase/migrations/042_app_releases.sql`）

`app_releases`：

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | uuid pk | |
| `version` | text unique | semver，如 `0.1.1` |
| `channel` | text default `'stable'` | 预留 beta |
| `min_supported_version` | text | **低于此版本强制更新** |
| `notes` | text | 更新说明（纯文本，≤2000 字） |
| `installer_url` | text | R2 上的**绝对**下载地址 |
| `installer_size` | bigint | |
| `sha512` | text | 与 latest.yml 一致（base64） |
| `blockmap_url` | text | 差分用 |
| `published_at` | timestamptz | |
| `published_by` | uuid | 发布人 |
| `state` | int default 1 | `1` 有效 / `0` 撤回 |

- RLS：`select` 给 `anon` + `authenticated`（仅 `state = 1`）；**`insert/update/delete` 不给任何客户端角色**，只有 service_role。理由：能写这张表 = 能推任意安装包。
- Storage：新建 public 桶 `releases`（只读），写权限同样只给 service_role。
- **不进快照**、**不 bump `dataset_version`** —— 发版不该让全员重下 7 MB 图片缓存。

## 4. 客户端

新增/改动：

| 文件 | 内容 |
|---|---|
| `src/main/updater.ts`（新） | 封装 `electron-updater`：事件转发、状态机、定时检查、`app.isPackaged` 守卫 |
| `src/shared/types/update.ts`（新） | `UpdateState` / `UpdateInfoLite` / `UpdaterApi` |
| `src/main/index.ts` | `registerUpdaterIpc()`；`whenReady` 后延迟启动检查 |
| `src/preload/index.ts` + `index.d.ts` | 暴露 `window.api.updater` |
| `src/renderer/src/views/SettingsView.vue` | 「关于与更新」区块：当前版本、检查按钮、进度条、说明、重启安装 |
| `src/renderer/src/components/UpdateDialog.vue`（新） | 有新版时的弹窗（强制模式不可关闭） |
| `electron-builder.yml` | `publish: {provider: s3, ...}`、显式 `win.icon`、`electronLanguages`、`compression: maximum` |
| `package.json` | `electron-updater`（**runtime 依赖**）、`release` 脚本 |
| `scripts/publish-release.mjs`（新） | 发布脚本 |

配置要点：

- `autoUpdater.autoDownload = false` —— 132 MB 的下载不该偷偷开始
- `autoUpdater.autoInstallOnAppQuit = true` —— 用户点「稍后」后，下次退出时自动装
- `autoUpdater.allowDowngrade = false` —— **不做降级**，回滚 = 发一个更高版本号的修复版
- `autoUpdater.logger = electron-log`（复用 T6.2）
- `app.isPackaged === false` → 全部跳过；`--dir` 绿色版没有 `app-update.yml`，必须 try/catch

行为规则：

| 场景 | 行为 |
|---|---|
| 检查时机 | 启动后 8 s、每 6 h、设置页手动 |
| 非强制新版 | **不弹窗**：侧栏/设置页红点 + 托盘 tooltip |
| 强制新版 | 模态弹窗，不可关闭，只能「立即更新」 |
| 下载 | 显示百分比；允许取消；断点由 Range 续传 |
| 下载完成 | 「重启并安装」→ `quitAndInstall(false, true)` |
| 检查失败 | **静默**，只记日志；仅手动检查时提示 |
| 离线 | 直接跳过，不报错（与 T6.1 的离线态一致） |
| 窗口在托盘 | 不打扰，等用户打开窗口 |

## 5. 发布流程（`scripts/publish-release.mjs`）

1. 校验 git 工作区干净、`package.json` 版本 **大于** 表里最大版本
2. `npm run build:win`
3. 读 `dist/latest.yml`，把 `files[].url` 改写成 R2 绝对地址（sha512 / size 原样保留）
4. 上传 `exe` + `.blockmap` 到 R2（同 key 覆盖，保留最近 3 个版本）
5. 上传改写后的 `latest.yml` 到 `releases/win/latest.yml`，`cacheControl: no-cache`
6. 用 **service_role** 写 `app_releases`（读 `.env.local` 的 `SUPABASE_SERVICE_ROLE_KEY` / `R2_*`）
7. 打印自检命令：`curl <supabase>/releases/win/latest.yml`

**service_role 绝不出现在客户端**：`electron.vite.config.ts` 的 `envPrefix` 只烘焙 `VITE_` / `MAIN_VITE_`，脚本用的密钥天然不会进 bundle；`.env.local` 也被 `electron-builder.yml` 的 `files` 排除。

## 6. 安全边界

- 安装包**无代码签名**（¥0 的代价），首次手动安装会有 SmartScreen 提示
- 完整性靠 yml 里的 `sha512`（electron-updater 内置校验）+ HTTPS
- R2 桶保持**私有**，下载走签名 URL 或公开只读端点（实现时定）；签名 URL 若会过期，则改用「公开只读 + 不可猜测路径」并接受链接可被转发
- 版本表写权限只在发布机，客户端连不上就降级为「无更新」，不阻塞启动

## 7. 冷启动与回滚

- **冷启动**：更新能力要等「带 updater 的安装版」装到用户机器才生效。**0.1.0 必须手动分发一次**，从 0.1.1 起才能自动更新
- **回滚**：不让客户端降级。线上出问题 → `state=0` 撤回该版本 + 立刻发一个更高版本号的修复版
- **存量**：R2 保留最近 3 个版本，Supabase 表保留全部发布记录（审计用）
