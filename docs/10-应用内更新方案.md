## 1. 为什么安装包不能放 Supabase Storage

T6.3 实测：`snooker-0.1.0-setup.exe` = **132 MB**（138,206,745 B）。对照 Supabase Free：

| 限制 | 官方数值 | 结论 |
|---|---|---|
| 单文件上传上限 | **50 MB**（Pro 才放宽） | 132 MB **传不上去**；裁掉 55 个语言包（49 MB 未压缩）也只到 ~120 MB |
| 月出口流量 | **5 GB**（另有 10 GB = 5 cached + 5 uncached 的口径） | 132 MB × 30 人 = **4 GB**，一次全量发版见底 |

## 2. 架构

```
发布机（本地脚本，持 SUPABASE_SERVICE_ROLE_KEY + GH_TOKEN）
  ├─ npm run build:win → exe / .blockmap / latest.yml
  ├─ GitHub REST：创建 release(v0.1.1) + 上传 exe / blockmap → 公开仓库
  ├─ 改写 latest.yml：files[].url 换成 GitHub 的绝对下载地址
  ├─ 上传 latest.yml → Supabase Storage（public 桶 releases/win/）
  └─ 写 app_releases 表 → Supabase Postgres（service_role）

客户端（几十台）
  ├─ electron-updater generic provider → Supabase 取 343 B 的 latest.yml
  │                     yml 里 files[].url 是 GitHub 绝对地址
  └─ 去 GitHub 下载 / 差分 / 校验 sha512 → 退出并静默安装
```

**为什么不让客户端直接用 `provider: github`**：那会走 `api.github.com`，公开请求限 60 次/小时/IP，且国内访问不稳定。改成 generic + 绝对 URL 后，客户端只向 Supabase 要清单（国内可达性好），下载才去 GitHub。

**关键技术依据**（已读源码确认）：`util.ts` 的 `newUrlFromBase` 用 `new URL(pathname, baseUrl)`，**清单里的绝对 URL 会被原样保留**，不会被拼到 base 上。

**已实测（2026-11-03，用 `images` 桶的真实对象）**：

| 验证项 | 结果 |
|---|---|
| 公开对象 + `?noCache=xxx`（electron-updater 一定会加） | **200**，参数被忽略，不影响取文件 |
| 响应缓存头 | `Cache-Control: private, no-cache` + `CF-Cache-Status: DYNAMIC` → **公开对象默认不缓存**，`latest.yml` 上传后立即生效，没有 CDN 旧清单问题 |

## 3. 数据模型（`supabase/migrations/042_app_releases.sql`）

`app_releases`：

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | uuid pk | |
| `version` | text unique | semver，如 `0.1.1` |
| `channel` | text default `'stable'` | 预留 beta |
| `min_supported_version` | text | **低于此版本强制更新** |
| `notes` | text | 更新说明（纯文本，≤2000 字） |
| `installer_url` | text | GitHub 上的**绝对**下载地址 |
| `installer_size` | bigint | |
| `sha512` | text | 与 latest.yml 一致（base64） |
| `blockmap_url` | text | 差分用 |
| `published_at` | timestamptz | |
| `published_by` | uuid | 发布人 |
| `state` | int default 1 | `1` 有效 / `0` 撤回 |

- RLS：`select` 给 `anon` + `authenticated`（仅 `state = 1`）；**`insert/update/delete` 不给任何客户端角色**，只有 service_role。理由：能写这张表 = 能推任意安装包。
- Storage：public 桶 `releases`（只读），写权限只给 service_role。
- **不进快照**、**不 bump `dataset_version`** —— 发版不该让全员重下 7 MB 图片缓存。

## 4.1 U2 实现要点（2026-11-03）

落地文件：`src/shared/types/update.ts`、`src/main/updater.ts`、`src/main/index.ts`（注册 + 启动）、
`src/preload/index.ts` + `index.d.ts`（`window.api.updater`）、`src/main/tray.ts`（tooltip）。

几个**后来才定下来**的细节，改动前先读：

1. **状态机只有一个真源**（主进程 `state`），渲染层只收快照。否则「设置页说有新版、侧栏红点没亮」这类不一致会反复出现。
2. **`min_supported_version` 不放 `latest.yml`**。electron-updater 的清单格式是固定的，塞不进自定义字段；也不让客户端读 `app_releases` 表（主进程没有 Supabase 客户端，为一个小字段引整套 SDK 不值）。改为发布脚本额外传一个 `policy.json` 到同一个 feed 目录，客户端按 `app-update.yml` 里的 `url` 拼 `/policy.json`。
3. **策略拉不到 = 不强制**（fail-open）。宁可让用户用旧版，也不能因为一个几百字节的文件超时就把所有人锁死；`policy.json` 的超时是 5 s，且不重试。
4. **取消下载用 `CancellationToken`**（来自 `builder-util-runtime`，已显式写进 `dependencies`）。`autoUpdater.cancellationToken` 是只读的内部令牌，复用会导致下一次下载一开就被取消。
5. **dev / 绿色版守卫**：`app.isPackaged === false` 直接判定 `unsupported`（不注册定时器，避免开发时每 6 小时往日志刷无效检查）；打包版再确认 `process.resourcesPath/app-update.yml` 存在。
6. **`quitAndInstall` 前必须先 `setQuitting(true)`**，否则窗口的 close 会把它拦回托盘，安装器根本起不来（与 T10.1 同一个坑）。
7. 托盘 tooltip 合并成三段：`斯诺克走位教学 · 后台运行中 · 有新版本 vX`，`setUpdateAvailable(null)` 清掉。

**U2 当时未验证的部分**（已由 U4 补齐，2026-11-03 见 §5.3 / §7）：真实安装版上「检查 → 下载 → 重启安装 → 版本号变化」整条链路。
现在这条链路已实测通过；dev 下 `phase` 仍恒为 `unsupported`，开发时看不到真实检查，属预期行为。

## 4.2 U3 实现要点（2026-11-03）

落地文件：`src/renderer/src/stores/update.ts`（新）、`src/renderer/src/components/UpdateDialog.vue`（新）、
`src/renderer/src/views/SettingsView.vue`、`src/renderer/src/components/layout/SideBar.vue`、`src/renderer/src/App.vue`、
`src/renderer/src/stores/index.ts`、`src/main/appInfo.ts` + `src/preload/index.ts` + `src/shared/types/system.ts`（`system.quit`）。

1. **订阅只有一份**：`bootstrapStores()` 里 `useUpdateStore().init()` 建唯一监听，侧栏 / 设置页 / 弹窗三个消费者读同一个 store。各自 `onState` 会让同一份快照被处理三遍，还容易漏退订。
2. **`init()` 先拉快照再订阅**：反过来的话，两步之间发生的状态变化会被漏掉。
3. **强制弹窗挂在 `App.vue`**（不是 `MainLayout`）：启动页、登录页同样可能需要拦截更新。
4. **「退出程序」走独立 IPC `app:quit` → `requestQuit()`**：关闭行为设成"最小化到托盘"时，窗口的 close 会被拦回托盘，直接 `app.quit()` 表现为"点了没反应"。
5. **强制弹窗的出口设计**：不做"稍后"（那等于可关），而是「退出程序」——网络差下载不下来时用户至少有一条路，不用去任务管理器杀进程。下载 `error` 阶段弹窗**保持打开**（`mandatory && info` 即显示），给「重试 / 退出程序」，否则点一次失败就绕过去了。
6. **红点位置**：侧栏吸底「系统设置」`pinned__icon` 右上角，`0.5rem` 圆点 + 2px 与侧栏底色同色的描边（压在图标上不糊）。
7. **`UpdateState` 全部原样展示**：渲染层不自己推导 `mandatory`、不自己比较版本号，否则迟早和主进程判断不一致。

**验收方式**：`out/` 构建后用 `electron . --remote-debugging-port=9222` 起真实主进程（有全套 IPC），
通过 CDP 注入 `unsupported / available / downloading 42% / downloaded` 四种快照截图核对亮暗两套主题。

## 5. 发布流程（`scripts/publish-release.mjs`）

1. 校验 git 工作区干净、`package.json` 版本 **大于** 表里最大版本
2. `npm run build:win`
3. GitHub REST：`POST /repos/<owner>/<repo>/releases`（tag `v<version>`）→ 上传 exe + blockmap 到 `uploads.github.com`
4. 读 `dist/latest.yml`，把 `files[].url` 改写成 GitHub 的 `releases/download/v<version>/<file>` 绝对地址（sha512 / size 原样保留）
5. 上传改写后的 `latest.yml` 到 `releases/win/latest.yml`（`cacheControl: no-cache`）
6. 用 **service_role** 写 `app_releases`
7. 打印自检命令：`curl <supabase>/releases/win/latest.yml`

**凭据边界**：`GH_TOKEN`（只需目标仓库的 `contents: write`）与 `SUPABASE_SERVICE_ROLE_KEY` 只存在发布机 `.env.local`；`electron.vite.config.ts` 的 `envPrefix` 只烘焙 `VITE_` / `MAIN_VITE_`，**绝不会进客户端**。

### 5.1 首次真实发布记录（2026-11-03 21:35）

| 项 | 实测 |
|---|---|
| release | `v0.1.0`，id `432738829`，tag 由 `package.json` 版本推出 |
| 上传 | 131.8 MB 用时 **135.6 s**（约 1 MB/s），blockmap 1.5 s |
| 清单 | `releases/win/latest.yml`，`cache-control: no-cache`，公开读 200 |
| 安装包 | 匿名 `302 → 200`，`Content-Length: 138206745`，与清单 `size` 一致 |
| 版本表 | `0.1.0 / stable / min 0.1.0 / state 1`；**anon 可 select**（RLS 生效） |

踩到的三个坑（都需写进流程，别人复现少走弯路）：

1. **fine-grained PAT 的 Contents 必须显式选 `Read and write`**，默认是 `Read-only`；报错是 `403 Resource not accessible by personal access token`，响应头 `x-accepted-github-permissions: contents=write` 会明确指出缺哪个权限。改权限**不换 token 值**，不用重新填 `.env.local`
2. **空仓库不能发 Release**：`422 Validation Failed / Repository is empty`。必须先有一次提交（本仓库已用 README 初始化）
3. **`gh()` 不能在非 2xx 时 `process.exit`**，否则外层靠 404 判断「release 尚不存在」的分支永远走不到（已修，`558fa1f`）

> 本机 `github.com` 的下载端点走代理会 502（`api.github.com` 正常），直连正常。Node 的 `https` 不读代理变量，正好走直连，与实测一致。


## 5.2 安装向导（NSIS，2026-11-03 改造）

**为什么改**：之前 `oneClick: true` 是一点就装的静默包，用户既不能选安装位置，也不能决定要不要建快捷方式。

| 配置 | 值 | 原因 |
|---|---|---|
| `oneClick` | `false` | 辅助式向导 |
| `allowToChangeInstallationDirectory` | `true` | 让用户选安装目录（静默升级时仍读注册表里的旧目录） |
| `createDesktopShortcut` / `createStartMenuShortcut` | `always` / `true` | **必须为真**，否则 electron-builder 既不会在卸载时清理，勾选框也无从「删除」 |
| `include` | `build/installer.nsh` | 自定义页与安装期逻辑 |

`build/installer.nsh` 三个要点（都踩过坑）：

1. `customInstallMode` 里 `StrCpy $isForceCurrentInstall "1"` → **强制 per-user 并跳过安装模式页**。如果允许「所有用户安装」，后续无 UAC 的静默升级会失败。
2. 勾选框页面函数**必须写在 `customPageAfterChangeDir` 宏内部**，不能放文件顶层——`installer.nsh` 被 include 时 MUI2 还没加载，`MUI_HEADER_TEXT` 会「macro not found」。
3. 整个文件用 `!ifndef BUILD_UNINSTALLER` 包住，否则卸载器那一趟报 `warning 6001 变量未用`，而 electron-builder 把警告当错误。
4. 文件必须带 **UTF-8 BOM**，否则中文按系统代码页解析，向导里是乱码。
5. 快捷方式是 electron-builder 在 `customInstall` **之前**建好的，所以 `customInstall` 里做的是「按勾选删掉不要的那个」，不是自己建。

### 5.2.1 首次安装走向导，升级全程静默（2026-11-04）

**要的行为**：第一次装 → 向导（选目录、选快捷方式、完成页）；应用内升级 → 什么都不问，装完自动重启。

**怎么区分**：electron-updater 拉起安装器时会带 **`--updated`**（见 `NsisUpdater.doInstall`），手动双击安装包没有这个参数。`build/installer.nsh` 的 `customInit` 里用 `${GetParameters}` + `${GetOptions}` 判断，命中就 `SetSilent silent`。

**为什么安装器侧也要判**：`/S` 是**调用方**传的，而升级时正在运行的是**旧版本**的代码。0.1.2 及更早调用的是 `quitAndInstall(false, true)`（不带 `/S`），只改客户端的话，这批用户还要再等一个版本才能享受到静默升级。判断放进安装器，第一次升级就生效。

**自动重启靠 `--force-run`**：electron-builder 的 `installSection.nsh` 里，辅助式安装器只有 `${if} ${isForceRun} ${andIf} ${Silent}` 才会 `doStartApp`。所以 `quitAndInstall` 的第二个参数必须是 `true`：

```ts
// src/main/updater.ts
updater.quitAndInstall(true, true)   // ① /S 静默 ② --force-run 装完自动拉起
```

**快捷方式不受影响**：升级时 `isTryToKeepShortcuts=true`，electron-builder 既不重建也不删除已有快捷方式；用户首次安装时取消过的桌面图标，升级后也不会自己长回来。

**验收（2026-11-04）**：
- 模拟老客户端 `setup.exe --updated --force-run`（**不带 `/S`**）：17.1 s 装完，进程 `MainWindowTitle` 全程为空（没有任何窗口），`D:\app\snooker\snooker.exe` 版本变化，应用自动拉起
- 不加参数双击：正常停在「Snooker 安装」向导（首次安装行为未变）
- 真实链路 0.1.3 → 0.1.4：设置页点「重启并安装」后无向导、无完成页，自动重启为 0.1.4


## 5.3 下载加速（2026-11-03 U4 实测后必改的一条）

**问题**：二进制在 GitHub Releases，但国内直连下载 **23 KB/s**，130 MB 要 **1.6 小时**。更新功能做完了却下不动，等于没做。

**实测**（同一台机器、同一条网络、`--noproxy` 直连，`curl --max-time` 取平均）：

| 源 | 速度 | 130 MB 耗时 |
|---|---|---|
| `github.com` 直连 | 23 KB/s | ~1.6 h |
| `ghfast.top` | 255 KB/s | ~8.5 min |
| `gh-proxy.com` | 100 KB/s | ~22 min |
| **`v4.gh-proxy.org`** | **8.8 MB/s（15 s 下完整包）** | **~15 s** |
| `github.moeyy.xyz` / `hub.gitmirror.com` / `ghproxy.cc` | 超时 / 不可用 | — |

**做法**：发布仍然发到 GitHub（开源项目的正规归档），但**清单里的 `url` 写成 `<镜像前缀><GitHub 原始地址>`**，客户端只按清单下载，所以换源不需要改客户端、不需要发新版。

- 前缀来自 `.env.local` 的 `GH_MIRROR`，默认 `https://v4.gh-proxy.org/`；留空 = 回退 GitHub 直连
- `app_releases.installer_url` 记的仍是 **GitHub 官方地址**（长期有效），镜像只活在清单里
- 镜像挂了：`node scripts/publish-release.mjs --manifest-only --min x.y.z` —— **秒级**重发清单，不重传 130 MB
- 清单自检会核对「公开清单里的下载地址与本次生成的一致」，防止改了前缀却没生效

**顺带验证到的差分下载**：0.1.1 → 0.1.2 时 electron-updater 走了 blockmap 差分，日志 `File has 48 changed blocks`、`To download: 949.52 KB (1%)`，**5 秒**拼出完整 130 MB 安装包并校验通过。前提是 `%LOCALAPPDATA%\snooker-updater\pending` 里有旧安装包；新装机首次更新仍是全量。

**验收（2026-11-03）**：`oneClick=false perMachine=false`；非静默启动停留并显示「Snooker 安装」窗口（一键包不会停）；`/S` 静默安装退出码 0、`InstallLocation` 与两个快捷方式都正确。

## 6. 安全边界

- 安装包**无代码签名**（¥0 的代价），首次手动安装会有 SmartScreen 提示
- 完整性靠 yml 里的 `sha512`（electron-updater 内置校验）+ HTTPS
- 公开发布仓库**只放二进制**，源码仓库保持私有；安装包里只有 publishable key（D22 已接受"拿到安装包就能拉已发布数据"）
- 版本表写权限只在发布机，客户端连不上就降级为「无更新」，不阻塞启动

## 7. 冷启动与回滚

- **冷启动**：更新能力要等「带 updater 的安装版」装到用户机器才生效。**0.1.0 必须手动分发一次**（群文件/U 盘，不占任何服务器流量），从 0.1.1 起才能自动更新
- **流量算术**：首次 132 MB 线下发；之后走 blockmap 差分，通常 10–30 MB。GitHub 的国内速度问题只作用在这 10–30 MB 上
- **回滚**：不让客户端降级。线上出问题 → `state=0` 撤回该版本 + 立刻发一个更高版本号的修复版
