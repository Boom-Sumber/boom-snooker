## 1. 为什么安装包不能放 Supabase Storage

T6.3 实测：`snooker-0.1.0-setup.exe` = **132 MB**（138,206,745 B）。对照 Supabase Free：

| 限制 | 官方数值 | 结论 |
|---|---|---|
| 单文件上传上限 | **50 MB**（Pro 才放宽） | 132 MB **传不上去**；裁掉 55 个语言包（49 MB 未压缩）也只到 ~120 MB |
| 月出口流量 | **5 GB**（另有 10 GB = 5 cached + 5 uncached 的口径） | 132 MB × 30 人 = **4 GB**，一次全量发版见底 |

## 2. 架构

```
发布机（本地脚本，持 SUPABASE_SERVICE_ROLE_KEY + GH_TOKEN）
  ├─ npm run build:win → exe / .blockmap / latest.yml
  ├─ GitHub REST：创建 release(v0.1.1) + 上传 exe / blockmap → 公开仓库
  ├─ 改写 latest.yml：files[].url 换成 GitHub 的绝对下载地址
  ├─ 上传 latest.yml → Supabase Storage（public 桶 releases/win/）
  └─ 写 app_releases 表 → Supabase Postgres（service_role）

客户端（几十台）
  ├─ electron-updater generic provider → Supabase 取 343 B 的 latest.yml
  │                     yml 里 files[].url 是 GitHub 绝对地址
  └─ 去 GitHub 下载 / 差分 / 校验 sha512 → 退出并静默安装
```

**为什么不让客户端直接用 `provider: github`**：那会走 `api.github.com`，公开请求限 60 次/小时/IP，且国内访问不稳定。改成 generic + 绝对 URL 后，客户端只向 Supabase 要清单（国内可达性好），下载才去 GitHub。

**关键技术依据**（已读源码确认）：`util.ts` 的 `newUrlFromBase` 用 `new URL(pathname, baseUrl)`，**清单里的绝对 URL 会被原样保留**，不会被拼到 base 上。

**已实测（2026-11-03，用 `images` 桶的真实对象）**：

| 验证项 | 结果 |
|---|---|
| 公开对象 + `?noCache=xxx`（electron-updater 一定会加） | **200**，参数被忽略，不影响取文件 |
| 响应缓存头 | `Cache-Control: private, no-cache` + `CF-Cache-Status: DYNAMIC` → **公开对象默认不缓存**，`latest.yml` 上传后立即生效，没有 CDN 旧清单问题 |

## 3. 数据模型（`supabase/migrations/042_app_releases.sql`）

`app_releases`：

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | uuid pk | |
| `version` | text unique | semver，如 `0.1.1` |
| `channel` | text default `'stable'` | 预留 beta |
| `min_supported_version` | text | **低于此版本强制更新** |
| `notes` | text | 更新说明（纯文本，≤2000 字） |
| `installer_url` | text | GitHub 上的**绝对**下载地址 |
| `installer_size` | bigint | |
| `sha512` | text | 与 latest.yml 一致（base64） |
| `blockmap_url` | text | 差分用 |
| `published_at` | timestamptz | |
| `published_by` | uuid | 发布人 |
| `state` | int default 1 | `1` 有效 / `0` 撤回 |

- RLS：`select` 给 `anon` + `authenticated`（仅 `state = 1`）；**`insert/update/delete` 不给任何客户端角色**，只有 service_role。理由：能写这张表 = 能推任意安装包。
- Storage：public 桶 `releases`（只读），写权限只给 service_role。
- **不进快照**、**不 bump `dataset_version`** —— 发版不该让全员重下 7 MB 图片缓存。

| 文件 | 内容 |
|---|---|
| `src/main/updater.ts`（新） | 封装 `electron-updater`：事件转发、状态机、定时检查、`app.isPackaged` 守卫 |
| `src/shared/types/update.ts`（新） | `UpdateState` / `UpdateInfoLite` / `UpdaterApi` |

| `src/preload/index.ts` + `index.d.ts` | 暴露 `window.api.updater` |
| `src/renderer/src/views/SettingsView.vue` | 「关于与更新」区块：当前版本、检查按钮、进度条、说明、重启安装 |
| `src/renderer/src/components/UpdateDialog.vue`（新） | 有新版时的弹窗（强制模式不可关闭） |
| `electron-builder.yml` | `publish: {provider: generic, url: <Supabase>/releases/win}`、显式 `win.icon` |
| `package.json` | `electron-updater`（**runtime 依赖**）、`release` 脚本 |
| `scripts/publish-release.mjs`（新） | 发布脚本 |

配置要点：

- `autoUpdater.autoDownload = false` —— 132 MB 的下载不该偷偷开始
- `autoUpdater.autoInstallOnAppQuit = true` —— 用户点「稍后」后，下次退出时自动装
- `autoUpdater.allowDowngrade = false` —— **不做降级**，回滚 = 发一个更高版本号的修复版
- `autoUpdater.logger = electron-log`（复用 T6.2）
- `app.isPackaged === false` → 全部跳过；`--dir` 绿色版没有 `app-update.yml`，必须 try/catch

行为规则：

| 场景 | 行为 |
|---|---|
| 检查时机 | 启动后 8 s、每 6 h、设置页手动 |
| 非强制新版 | **不弹窗**：侧栏/设置页红点 + 托盘 tooltip |
| 强制新版 | 模态弹窗，不可关闭，只能「立即更新」 |
| 下载 | 显示百分比；允许取消；断点由 Range 续传 |
| 下载完成 | 「重启并安装」→ `quitAndInstall(false, true)` |
| 检查失败 | **静默**，只记日志；仅手动检查时提示 |
| 离线 | 直接跳过，不报错（与 T6.1 的离线态一致） |
| 窗口在托盘 | 不打扰，等用户打开窗口 |

## 5. 发布流程（`scripts/publish-release.mjs`）

1. 校验 git 工作区干净、`package.json` 版本 **大于** 表里最大版本
2. `npm run build:win`
3. GitHub REST：`POST /repos/<owner>/<repo>/releases`（tag `v<version>`）→ 上传 exe + blockmap 到 `uploads.github.com`
4. 读 `dist/latest.yml`，把 `files[].url` 改写成 GitHub 的 `releases/download/v<version>/<file>` 绝对地址（sha512 / size 原样保留）
5. 上传改写后的 `latest.yml` 到 `releases/win/latest.yml`（`cacheControl: no-cache`）
6. 用 **service_role** 写 `app_releases`
7. 打印自检命令：`curl <supabase>/releases/win/latest.yml`

**凭据边界**：`GH_TOKEN`（只需目标仓库的 `contents: write`）与 `SUPABASE_SERVICE_ROLE_KEY` 只存在发布机 `.env.local`；`electron.vite.config.ts` 的 `envPrefix` 只烘焙 `VITE_` / `MAIN_VITE_`，**绝不会进客户端**。

## 6. 安全边界

- 安装包**无代码签名**（¥0 的代价），首次手动安装会有 SmartScreen 提示
- 完整性靠 yml 里的 `sha512`（electron-updater 内置校验）+ HTTPS
- 公开发布仓库**只放二进制**，源码仓库保持私有；安装包里只有 publishable key（D22 已接受"拿到安装包就能拉已发布数据"）
- 版本表写权限只在发布机，客户端连不上就降级为「无更新」，不阻塞启动

## 7. 冷启动与回滚

- **冷启动**：更新能力要等「带 updater 的安装版」装到用户机器才生效。**0.1.0 必须手动分发一次**（群文件/U 盘，不占任何服务器流量），从 0.1.1 起才能自动更新
- **流量算术**：首次 132 MB 线下发；之后走 blockmap 差分，通常 10–30 MB。GitHub 的国内速度问题只作用在这 10–30 MB 上
- **回滚**：不让客户端降级。线上出问题 → `state=0` 撤回该版本 + 立刻发一个更高版本号的修复版

## 8. 任务拆解

| ID | 任务 | 产出 | 验收 |

| **U1** | 发布通道 | `042_app_releases.sql`（表 + RLS + `releases` 桶）、`scripts/publish-release.mjs` | 脚本能发一版并写表；`curl` 拿到正确 `latest.yml`；手工下载能装 |
